# Relivio AI Risk Assessment Service

A small, **explainable, rules-based** scoring service that assists — never
decides — community voting on emergency requests, campaign milestones, and
whole campaigns/organizers. It cannot approve, reject, freeze, or confiscate
funds; governance and the smart contracts always retain full control. This
is deliberately rules-based rather than an opaque ML model, because every
point on every score needs to be traceable to a named reason for a
life-impacting financial decision.

## Endpoints

| Endpoint | Used when | Frontend caller |
|---|---|---|
| `POST /assess/request` | Someone submits an emergency-assistance request to a `CommunityFund` | `assessRequestRisk` in `frontend/lib/aiRisk.ts`, rendered in `CreateRequestPanel.tsx` |
| `POST /assess/milestone` | An organizer proposes releasing a campaign milestone | `assessMilestoneRisk`, rendered in `MilestoneCard.tsx` |
| `POST /assess/campaign` | A campaign is created (or a verifier reviews it) — organizer wallet history, campaign history, donor concentration, metadata completeness | `assessCampaignRisk`, rendered in `app/campaigns/create/page.tsx` |
| `GET /health` | Liveness check | — |

Every response has the same shape:

```json
{
  "risk_level": "LOW | MEDIUM | HIGH",
  "risk_score": 0,
  "reasons": ["Each score point traces back to one of these."],
  "disclaimer": "Advisory only. This score does not approve, reject, freeze, or confiscate anything — governance and the smart contracts retain full control."
}
```

## Run locally

```bash
cd ai
python3 -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt
uvicorn services.main:app --reload --port 8000
```

The frontend expects this service at `NEXT_PUBLIC_AI_SERVICE_URL`
(defaults to `http://localhost:8000` if unset — see `frontend/.env.example`
at the repo root).

Interactive docs (Swagger UI) are auto-generated by FastAPI at
`http://localhost:8000/docs` once the service is running — useful for
poking at each endpoint by hand without touching the frontend.

## Run the tests

```bash
cd ai
pip install -r requirements-dev.txt
pytest -v
```

`tests/test_main.py` hits every scoring rule directly through FastAPI's
`TestClient` (no running server needed) — one test per rule, named after
what it checks, plus a `TestNeverAutoDecides` class that asserts the
response never contains an approve/reject/decision field. If a rule in
`services/main.py` changes behavior, the failing test name should point
straight at which rule broke.

## Design notes / why the scoring looks the way it does

- **All rules are additive and capped at 0–100.** No rule can push a score
  negative, and the total is clamped to 100 even if every signal fires at
  once (see `test_score_never_exceeds_100` in each endpoint's tests).
- **Wallet age / tx count are *skipped* once there's a track record.** An
  organizer with released milestones, or with prior campaigns on the
  platform, has already demonstrated legitimacy — a fresh wallet only
  matters for first-timers. This is intentional, not an oversight; see
  `test_wallet_age_skipped_for_returning_organizer` and
  `test_new_wallet_ignored_once_organizer_has_track_record`.
- **Donor concentration** (`/assess/campaign`) flags the classic
  wash-trading / self-funding pattern — a handful of wallets accounting for
  most of the funds raised — without accusing anyone of anything; it's
  surfaced as a reason string a human voter or verifier can weigh.
- **This service has no RPC or database connection by design.** Wallet age,
  tx counts, donor counts, and prior-campaign counts must be supplied by the
  caller (the frontend via `viem`, or pulled from Supabase/the indexer).
  Keeping this service stateless keeps it trivial to test, trivial to
  redeploy, and impossible for it to accidentally become a hidden source of
  truth that overrides on-chain state.

## Extending

To add a new signal: add a field to the relevant Pydantic input model (with
a sensible neutral default so existing callers don't break), add the scoring
rule in the matching endpoint function with a human-readable reason string,
and add at least one test asserting the reason string appears when the
signal fires and doesn't appear when it doesn't.
